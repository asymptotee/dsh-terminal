# 记忆系统：原理与机制

> 基于 deepseek-harness monorepo 的真实源码与文档整理：`packages/context/
> agent-instructions`（指令记忆）、`packages/session/`（会话持久化）；
> 消费侧基于 dsh-terminal 的实现。
> 姊妹篇：《会话事件词汇表》讲事件模型，《Subagent 基本原理与实现》讲上下文隔离，
> 《沙箱机制》讲执行边界。

# 第一部分：记忆层次总览

## 1.1 层次模型

dsh 的记忆分为清晰的两层——短期记忆与长期记忆：

```
┌─ 短期记忆（工作记忆）─────────────────────────┐
│  模型上下文窗口 —— 当前请求携带的消息          │
│  有界、昂贵、随 token 压力增长                 │
└──────────────────────────────────────────────┘
┌─ 长期记忆（持久）────────────────────────────┐
│  ① 会话日志（事件溯源，可重放）               │
│  ② 指令文件（AGENTS.md / CLAUDE.md 层级）    │
└──────────────────────────────────────────────┘
```

## 1.2 一句话定位

**上下文窗口是短期记忆，完整会话日志是长期记忆（主要形态），指令文件是跨会话的
规则性记忆**。dsh 没有「agent 自写记忆」这一层（见 4.1）。

# 第二部分：短期记忆——上下文窗口

## 2.1 是什么

模型每次请求携带的消息历史——系统提示、指令基线、用户消息、assistant 消息、工具
调用与结果全部占用窗口空间。有界（模型上下文上限）、昂贵（每次请求都要重新计费/
处理）、随对话推进持续增长。

## 2.2 如何观测

- **数据来源**：`assistant/message` 事件的 `usage`（inputTokens + cacheReadTokens）
  给出最近一步的真实窗口占用；模型窗口上限经 LLM 服务的模型信息查询获得
- **UI 呈现**：TUI 状态栏的 `context: <used>/<window> (<pct>%)`——用量比随每一步
  的报告刷新；窗口查询在后台进行，首帧不等待它
- **KV cache 视角**：请求前缀的稳定性决定缓存复用——指令注入等机制都刻意设计为
  「append-only、不破坏已缓存前缀」（见 3.2）

# 第三部分：长期记忆

## 3.1 会话日志（主要形态）

dsh 记忆体系的核心，直接来自事件溯源架构（详见《会话事件词汇表》）：

- 每次对话的**完整事件流**持久化——消息、工具调用与结果、todo 快照、沙箱模式切换……
  一切发生过的都是日志里的不可变事件
- **恢复 = 重放**：`--resume <id>` 把持久日志重放进 fold，显示与状态完整重建
- 所以「上次聊到哪」不靠摘要，靠**完整日志**——这是与许多 agent 系统的本质区别：
  记忆不是摘要后的印象，是逐字节的事实记录

## 3.2 指令文件（`dsh-agent-instructions`）

跨会话的**规则性记忆**——人类书写、agent 读取，与 Claude Code 的记忆文件同构。

**文件体系**：

| 层级 | 文件 | 说明 |
|---|---|---|
| 用户全局 | `$DSH_HOME/AGENTS.md` | 无本地 overlay |
| 项目各级目录 | 从项目根（默认 `.git` 标记定位）到会话 cwd 的**每个目录** | 基础候选 `AGENTS.md`、`CLAUDE.md`；本地 overlay `AGENTS.local.md`、`CLAUDE.local.md` |

**注入方式**——会话第一个合格 pre-step 时把基线折入持久历史：一条 **user 角色持久
消息**，用 `<system-reminder>` 框架包裹：

```md
<system-reminder>
The following workspace instructions may be relevant to your work. ...
Instructions from: ~/.dsh/AGENTS.md
...
Instructions from: AGENTS.md
...
</system-reminder>
```

指令内容里的字面 `</system-reminder>` 文本会被转义——仓库控制的文本无法关闭插件
控制的框架。

**动态发现**——没有文件 watcher：在成功的 `read` / `write` / `edit` 工具调用后检查
新到达的目录 scope：

| 情况 | 注入消息 |
|---|---|
| 嵌套指令文件出现 | `Additional instructions from: <path>`（新 scope） |
| 文件内容改变 | `Updated instructions from: <path>`（替代之前加载的内容） |
| 文件消失 / 成为同目录更早候选的重复 | `Instructions removed: <path>` |

**细节机制**：

- **同级去重**：`CLAUDE.md` 与 `AGENTS.md` 去除首尾空白后字节一致 → 只渲染一次
  （按候选顺序归到最早的）
- **防重复注入**：路径 + SHA-1 内容 digest 双键——两者都未变不重复注入；digest
  持久化在带类型的消息来源里，跨恢复存活
- **预算**（`maxBytes`，必填）：超限时**优先保最具体的文件**——先丢弃完整的较宽泛
  文件，再截断最具体文件，并发出可见的预算通知
- **恢复对账**：恢复的会话保留兼容的可见基线，只追加当前文件的转换（set/replace/
  remove）；发现/优先级/项目根/预算标识变化时，用一条完整基线显式取代旧基线

# 第四部分：边界与对比

## 4.1 关键的「没有」：agent 不自写记忆

与 Claude Code 的显著差异：

| | Claude Code | dsh |
|---|---|---|
| 跨会话记忆来源 | 人写的 + **agent 自写的 memory 文件**（自动沉淀学到的事实，跨会话加载） | 人写的指令文件 + resume 旧会话 |
| agent 写记忆的工具 | 有 | **没有**——源码中无自写记忆机制 |

dsh 的设计哲学：**会话日志就是完整记忆，需要跨会话的东西由人写进 AGENTS.md**——
没有「agent 自己记笔记」这一层。想要类似效果，目前只能靠人类维护指令文件。

## 4.2 子代理的记忆隔离

每个子代理烧**自己的**上下文窗口（独立会话、独立日志），只把蒸馏结果回流父级——
这本身就是一种记忆管理策略：冗长的中间过程留在子级日志里，父级窗口只增加一条
结果（详见《Subagent 基本原理与实现》1.1 节）。

## 4.3 dsh-terminal 的角色

TUI 只做两件事，记忆机制全部在 harness 层：

- 状态栏显示上下文用量（短期记忆的观测面）
- 指令注入消息的渲染（notice 形态的注入走 notice 帧）

# 一句话总结

**dsh 的记忆 = 上下文窗口（短期）+ 完整会话日志（长期、可重放的事实记录）+ 人写
指令文件（跨会话规则）；与 Claude Code 相比缺「agent 自写记忆」层——跨会话知识的
沉淀权在人类手里。**
